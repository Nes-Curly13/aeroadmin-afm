# S7 — Fase 1: UI para capturar 9 campos del Excel

**Sprint**: feature/s7-schema-extension
**Estado Fase 0**: merged (PR #12)
**Branch para Fase 1**: `feature/s7-ui-capture` (basado en `feature/s7-schema-extension`)
**Dependencia**: migration `20260824000000_add_excel_fields_schema.sql` aplicada a Supabase

## Contexto

El operador fumigador vuela drones y al final del día llena un Excel
con 9-10 campos que DJI SmartFarm no expone. Fase 0 extendió el schema
(2 catálogos, 5 cols operativas, 1 tabla de invoices). Fase 1 agrega
la UI para que el operador capture esos campos manualmente desde la
web (no desde el Excel — la captura es en el form al registrar o
editar una fumigación, y en el detail page).

## Decisiones tomadas en el plan v2

1. **NO se importan datos históricos.** El sistema arranca limpio. La
   UI captura campos para fumigaciones NUEVAS.
2. **Captura es POR-FUMIGACIÓN, no por-vuelo.** Los 4 cols en
   `dji_flights` (vehicle, zona, horas_planta, area_ot) NO tienen
   UI en este sprint. Razón: el form actual es de fumigaciones (no
   de vuelos), y meter UI de flight-level complica el flujo del
   operador. Esos campos quedan en BD pero se llenan cuando se
   importe data de la nube DJI (futuro). Ver Q abajo.
3. **Invoices SÍ tienen UI.** Es 1:N con fumigaciones — la UI
   lista facturas en el detail page.
4. **Vehicle picker en el form de fumigación, no en el form de
   vuelo.** La fumigación es la entidad que el operador registra
   manualmente; el vehicle es contexto operativo. Decisión discutible
   (ver Q).

## Questions para el user (Q abiertas)

### Q1. ¿Vehicle va en el form de fumigación o en el form de vuelo?
Recomendación: fumigación. Razón: el form actual es de fumigación, y
forzar al operador a registrar vuelo manual es scope nuevo.

### Q2. ¿Catálogo `application_types` server-fetched o client-hardcoded?
Recomendación: client-hardcoded (mismo patrón que `FUMIGATION_CATEGORIES`).
El catálogo casi no cambia (seed 4 slugs). Server-fetched agregaría
un round-trip a cada load del form.

### Q3. ¿Invoices editables o solo crear+cancelar?
Recomendación: crear+cancelar (soft). Razón: si una factura tiene
error de número, lo más limpio es cancelarla y crear una nueva
(cheque/numero es unique por fumigación).

### Q4. ¿Filtro `application_type` en `/fumigaciones`?
Recomendación: sí, chip-style como los filtros existentes.
Mismo patrón que `category_id`.

## PR-B — diseño detallado

### API endpoints

#### `GET /api/admin/dji-vehicles?search=ABC&limit=10`
- Auth: admin o supervisor (lectura controlada; cualquier rol
  autenticado podría leer, pero por consistencia con el resto del
  codebase exigimos admin/supervisor).
- Query params:
  - `search` (opcional, default ""): filtra por `plate ILIKE %search%`.
    Si vacío, devuelve los 10 más recientes (`ORDER BY created_at DESC`).
  - `limit` (opcional, default 10, max 50).
- Response: `{ vehicles: DjiVehicle[] }`.
- Status: 200.

#### `POST /api/admin/dji-vehicles`
- Auth: admin o supervisor.
- Body: `{ plate: string, description?: string }`.
- Server-side:
  - Trim + uppercase plate.
  - Validar regex `^[A-Z0-9-]{3,12}$` (mismo que la BD CHECK).
  - Si ya existe (`findDjiVehicleByPlate`), devolver 200 con el row
    existente (idempotente — el form de creación lo usa con seguridad).
  - Si no, INSERT y devolver 201 con el row nuevo.
- Errores: 400 (body inválido), 401/403 (auth), 500 (interno).
- NO 409: idempotente para que el form pueda llamarlo sin miedo a
  duplicados.

### Componente `VehiclePicker`

Patrón basado en `components/parcels/parcel-picker.tsx`. La
complejidad es el autocomplete con debounce + creación on-the-fly.

#### UX:
- Input text con placeholder "ej. ABC-1234"
- Dropdown que muestra hasta 5 matches con plate + description
- Click en match → selecciona
- Si la búsqueda no matchea después de 300ms, aparece opción
  "+ Crear 'ABC-1234' como nuevo vehículo"
- Click en "+ Crear" → POST + selecciona
- Estado vacío: "Empieza a escribir la placa"

#### Props:
```ts
interface VehiclePickerProps {
  value: DjiVehicle | null;        // vehículo seleccionado
  onChange: (v: DjiVehicle | null) => void;
  disabled?: boolean;
  name?: string;                   // para form integration (hidden input)
}
```

#### Implementación:
- `useState` local para query + results + loading + isCreating
- `useEffect` con debounce (300ms) que llama a `GET /api/admin/dji-vehicles?search=X`
- Refs para evitar race conditions cuando el usuario tipea rápido
- `aria-activedescendant` para accesibilidad del dropdown
- Keyboard nav: ArrowDown/Up/Enter/Esc

### Form integration

- En `RegisterFumigationForm`, agregar campo `vehicle_plate: string`
  en FormState
- `fromFumigation()`: hidrata desde `f.vehicle_plate` (que
  necesitaremos proyectar en `getFumigationById` via JOIN con
  `dji_flights` → `dji_vehicles`, agregación del más frecuente)
- UI: agregar `<VehiclePicker>` después de "Dron usado"
- Body: enviar `vehicle_plate: string` (el form es responsable
  de convertir DjiVehicle → string en el PATCH)

### Caveat: persistencia del vehicle_plate en fumigación

Por ahora guardamos `vehicle_plate` como campo `notes->vehicle_plate`
(jsonb) en `dji_fumigations.notes` — la fumigación NO tiene una col
`vehicle_id` directa. Razón: la decisión del plan fue que el vehicle
es per-flight (no per-fumigation), y el form es de fumigación.
Workaround temporal: meter el plate en el notes jsonb. NO contamina
el modelo y queda accesible.

Si en el futuro se decide persistir a nivel fumigación, se agrega
`dji_fumigations.vehicle_id FK dji_vehicles` en una migration nueva.
