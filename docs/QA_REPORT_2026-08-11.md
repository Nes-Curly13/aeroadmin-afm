## 7. Findings detail

### F1 [CRÍTICO] — Hardcoded `dose_l_ha: 2.0` en `lib/data.ts:331` muestra valor falso al operador

- **File**: `lib/data.ts:331` (función `adaptSchedule`)
- **Qué**: `dose_l_ha: 2.0, // el proyecto no tiene este campo en schedule — default razonable`
- **Por qué importa**: el parcel detail page (`app/parcelas/[id]/page.tsx`) lee `schedule.dose_l_ha` y lo muestra como "Dosis: 2.0 L/ha" en la ficha técnica. **95% de las fumigaciones del dataset DJI histórico tienen `dose_l_per_ha = NULL` en la BD** (640 de 642 fumigaciones). El operador ve "2.0 L/ha" como si fuera dato real, pero es un default inventado. El PDF de reportes (que lee la BD directo) muestra la verdad.
- **Evidencia**: `docs/audit/DOSE_FIELDS_BACKFILL.md:37-44` documenta el problema explícitamente:
  > "El V0 adapter de `lib/data.ts:331` hardcodea `dose_l_ha: 2.0` para todas las parcelas cuando arma el `ParcelSummary`... Eso da la sensación al operador de que el dato existe, pero es un default falso."
- **Fix sugerido**:
  - Opción A (rápida): cambiar el default a `null` y mostrar "—" en el detail page cuando es null.
  - Opción B (correcta): agregar `dose_l_per_ha` al `DjiFumigationScheduleV0` (en `lib/types.ts`) con el primer valor real que encuentre (last fumigation's dose, o schedule's static dose, o null) y migrar el detail page a leerlo.
  - Opción C (la del doc): documentar como **feature bloqueada por backend** y mostrar un callout amarillo en el detail page que diga "Dosis histórica no disponible — DJI no expone el dato".

- **Fix sugerido**:

## 8. Reusable QA template notes

### Qué funcionó bien

- **Procedimiento por fases + per-user-story** da cobertura sistemática. La matriz de status (✅/⚠️/❌) por user story es fácil de escanear.
- **Correr arch:check, build, tests en una sola pasada** al principio (Phase 1) detecta problemas estructurales antes de meterse en detail.
- **Greps paralelos** sobre `@/lib/alerts`, `@/lib/db`, etc. en `app/`, `components/`, `api/`, `scripts/` son la forma más rápida de detectar drift arquitectónico. La R1 tiene un agujero: solo prohibe `pg` directo, no `lib/db` directo.
- **Buscar `arch:check` orphan infos** y cruzar con el coverage report es una forma barata de detectar código muerto. Los 6 orphans de este QA son exactamente los archivos que nadie en producción importa.
- **El DOSE_FIELDS_BACKFILL.md es una joyita**: la auditoría previa (feature/reports-level-2) documentó el bug pero **no lo arregló**. Como agente de QA, mi trabajo fue detectarlo y reportarlo, no arreglarlo (es policy: "DO NOT modify code. Read-only QA.").

### Qué mejorar para el próximo QA pass

- **No confiar en coverage global** sin leer el vitest.config. El "75/70" de AGENTS.md es aspiracional; el gate real es 45/65. **El próximo QA debe leer `vitest.config.ts` antes de medir coverage** y reportar el gap entre la aspiración y la realidad.
- **Medir el delta entre el último QA y este** si el repo tiene CI que produce reports de coverage. Esto es factible: `coverage/lcov.info` se regenera cada `npm run test:coverage`. Comparar con un baseline.
- **Correr `npm run dev` localmente y abrir las 12 pages** no fue posible en este QA (sin browser interactivo, sin DB). El próximo QA debe hacerlo o pedirle al dev que lo haga. Las páginas podrían compilar y los tests pasar pero renderizar feo o con errores runtime.
- **No asumir que "no errors" = "OK"**. El `arch:check` tiene 6 orphans infos que están en `severity: "info"` — no bloquean, pero señalan drift. El QA debe leer los infos también, no solo los errors y warnings.
- **Para tests faltantes**: la spec de cobertura de los **user stories** específicas (no los archivos) no se mide. ¿Hay tests E2E para el flow "operador mira el detail de una fumigación"? El `tests/user-story-dashboard-e2e.test.ts` cubre 4 escenarios del dashboard pero está excluido del vitest config (requiere DB). Para el resto de las 12 pages, **no hay E2E tests con DB real** — solo tests de components aislados.

### Adiciones sugeridas para el próximo QA

- **Snapshot de las dependencias** (`package.json` + lockfile) — útil para detectar upgrades riesgosos. Hoy Next 16.2.4, React 19.2.5.
